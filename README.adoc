This repository contains my personal configuration files (dotfiles) for my Ubuntu-based development environment.
It is designed to be automated, preset-aware, and easily deployed on a new machine.

The core of this setup uses *GNU Stow* to manage symlinks and the `dfctl` Python CLI to orchestrate the entire installation, including applications, repositories, and preset-specific settings.

== Key Features

* *GNU Stow*: Uses `stow` to manage all dotfiles, keeping them neatly organized in this repo and symlinked to their correct locations in `$HOME` or `/`.
* *Preset-Aware Setup*: `dfctl apply` takes a `--preset work`, `--preset personal`, or `--preset homelab` argument (and reuses the saved preset on later runs).
It then installs the correct applications and builds the right configuration files based on this preset (see "Presets and the Overlay" below for how presets are resolved and extended).
* *Declarative `apt` Sources*: All third-party `apt` repositories (like Google Chrome, VS Code, 1Password) are declaratively managed using `.sources` files in the `apt/` package.
The setup script securely downloads the latest GPG keys during installation.
* *Snap-Free*: `snapd` is automatically removed and blocked via an `apt` preference file (`system/` package) for a cleaner system.
* *Zsh Function Autoloading*: Custom Zsh functions are stored in `~/.config/zsh/functions` and loaded efficiently using `fpath` and `autoload`.
* *Zsh Completions*: Tab-completion scripts for custom commands live in `$ZSH_CUSTOM/completions` (`omz/.oh-my-zsh/custom/completions/`), which oh-my-zsh adds to `fpath` before `compinit` — e.g. `_flaky-it` and `_kdev`.
* *Automated Binary Installation*: Downloads and installs specific `.deb` packages from GitHub releases (like `lsd` and `bat`) based on a text list.
* *Secure & Separate Configs*:
** *Claude Code Profiles*: Per-preset Claude Code settings (`claude_work.json`, `claude_personal.json`, `claude_homelab.json`) live in `~/.dotfiles/claude-profiles/`. `dfctl apply` merges the preset's file into the generated `~/.claude/settings.json`, after the base `claude/.claude/settings.json` and before the overlay's `claude-settings/settings.json` and `claude-profiles/<preset>.json`.
** *Extra Claude accounts*: `claude-account create <name>` makes one, `update`, `rename`, `remove` (asks first; `--yes` skips the prompt) and `ls` manage them, and `claude --account <name>` (or `claude --burst` for `burst`) runs Claude Code on it. Its config dir, `~/.claude-<name>`, links in everything from `~/.claude` except the login and account file, so settings, sessions and plugins are shared; `/login` once with the new account. `claude-account create|update` take `--telemetry on|off`, `--label <key>=<value>`, `--otel-account <label>` and `--api-key-env <VAR>` (the name of a `secrets.env` variable that becomes `ANTHROPIC_API_KEY`; the key itself is never stored). `claude --with <name>[,<name>...]` enables MCP servers for one session; a bare `--with` reuses the account's last selection.
** *Claude usage telemetry*: on the `personal` and `homelab` presets, `claude` exports OTel metrics and events labelled with the account, host (the preset), machine (the hostname) and project to the collector (`CLAUDE_OTEL_ENDPOINT` overrides the address). Foothold sessions send the same labels, with the project fixed to their start directory. The `work` preset sends none, and `claude-account update <name> --telemetry off` silences one account.
** *Claude Remote Foothold*: on the `personal` and `homelab` presets, `dfctl apply` enables user lingering and installs systemd user units that start Remote Control sessions in tmux at boot: one named after the hostname for the main account (attach with `tmux attach -t claude-foothold`), and one named `<hostname>-burst` for the `burst` account once it has logged in (attach with `tmux attach -t claude-foothold-burst`). The `work` preset runs none. Which accounts get one is the preset's `footholds` list.
** *Secret Configs*: True secrets (API keys, tokens) are ignored by Git.
They should be manually placed in `~/.config/dotfiles/secrets.env` (mode 600), which both `.zshrc` and the foothold unit load.

== Installation on a New Machine

=== Clone the Repository

[source,bash]
.Install git first
----
sudo apt update && sudo apt install git -y
----

[source,bash]
.Then, clone this repository to your home directory as `.dotfiles`.
----
git clone <your-repo-url> ~/.dotfiles
----

=== Run the Setup Script

[source,bash]
.Bootstrap this machine from your home directory, specifying the machine preset.
----
~/.dotfiles/bin/dfctl apply --preset work
# or
~/.dotfiles/bin/dfctl apply --preset personal
# or
~/.dotfiles/bin/dfctl apply --preset homelab
----

After checking `~/.claude/settings.json` for hand edits since the last install (stops with exit 3 unless `--accept-drift`), it fetches this repo, and
the `~/.dotfiles-overlay` overlay when it is a git checkout, and fast-forwards each when new commits exist, so
presets and package lists are current; a failed fetch or
fast-forward (dirty tree, diverged branch) only warns. The first time you run it for a preset on this
machine it prompts for your git name, email, and (optionally) an SSH signing key, and writes them to
`~/.gitconfig.local`; it resolves the preset's package lists, minus your opt-outs in
`~/.config/dotfiles/packages/<preset>.txt`; and it detects any `~/.dotfiles-overlay` overlay and layers
it in (see "Presets and the Overlay" below for all three). It then runs the install steps itself
to actually install packages, stow the dotfiles, and configure your Claude Code profile — which is where
the `sudo` password prompt and the rest of the guided process come from. If a step fails, it offers to roll
back the changes it recorded in `~/.dotfiles-setup-rollback.log` (stowed packages, backed-up and generated
system files, docker group membership) and to reinstall the apt and Flatpak packages it removed. Removed
`.deb`-backed packages (Zoom, GitHub pins) only get a warning to reinstall them manually, and
packages the install added are not uninstalled.

`dfctl apply` also accepts `--dry-run`, `-v`/`-vv`/`-vvv` (verbosity), `--reconfigure` (re-prompt for the git identity), `--accept-drift`, `--prune` (remove no-longer-wanted packages without the confirmation prompt; apt removals run only in the system stage) and `-y`/`--yes` (apply without the "Continue?" question; a run with no terminal needs it whenever the plan changes packages). `apply` prints a plan first (what apt, Flatpak, the GitHub `.deb` pins, the user tools and the sudo steps would install, the dotfile links it would create, a pending move of `~/.dotfiles-private` to `~/.dotfiles-overlay`, and which removals are pending) and asks `Continue? [y/N]` only when the plan changes something. Declining (exit 6) or running without a terminal and without `--yes` (exit 5) skips every install step and the overlay move; the `git pull` of the dotfiles and overlay checkouts that precedes the plan still happens. Declining exits 6 and leaves the machine as it was; with no terminal and no `--yes` a changing plan exits 5. `--dry-run` prints the plan and the "Would ..." lines of the few steps a plan cannot check (apt sources, post-apt tools, Claude tools, the default terminal).

[NOTE]
If stow fails because existing files block a symlink, re-run with `--force`. Each blocking file moves to
`~/.local/state/dotfiles/stow-backups/<timestamp>/<path relative to $HOME>` and is logged, so restoring it
is a plain `mv`.

[NOTE]
If you get a "Permission denied" error, your clone may not have preserved the executable bits.
Run `chmod +x ~/.dotfiles/bin/dfctl ~/.dotfiles/bin/dotfiles-backup` and try again.

=== Manual Steps

==== Add Secrets
If you have any secret keys, tokens, or private environment variables, add them to `~/.config/dotfiles/secrets.env` as plain `KEY=value` lines, with no `export` prefix and no `$` or backslashes in values:

[source,bash]
.Example:
----
install -m 600 /dev/null ~/.config/dotfiles/secrets.env
echo "GITHUB_TOKEN='your-secret-token'" >> ~/.config/dotfiles/secrets.env
----

==== Git Configuration

The setup stows `~/.dotfiles/git/.gitconfig` to `~/.gitconfig`, which carries no identity of its own. Running `dfctl apply --preset <name>` (above) is what supplies it: the first time you run it on a machine, it prompts for your git name, email, and (optionally) an SSH signing key, and writes them to `~/.gitconfig.local`, which `.gitconfig` includes unconditionally. `.gitconfig` also conditionally includes `~/.dotfiles-overlay/git/gitconfig-work` — from the optional overlay described below — to override `user.email` when your remote points at a Collibra `github.com` repo.

`git tidy` (the zsh function `git-tidy`) cleans up after merged work: it fetches without pruning your remote-tracking refs, then deletes local branches already merged into origin's default branch, including squash- and rebase-merged ones, and removes their worktrees. It shows the plan and asks first (`--yes` skips the prompt, `--dry-run` only shows it, `--base <ref>` picks another base). It keeps `main`, `master`, `develop`, anything checked out in the main or current worktree, a branch still at the base tip, a worktree that is locked or has uncommitted changes, and a branch whose upstream is gone but whose work is not in the base.

=== Restart Your Shell

Open a new terminal or run `zsh` to load your new environment.

== How to Maintain This Repo

=== Updating Applications

To add or remove applications, *do not* use `apt-get install` directly.
Instead, edit the package lists in the `packages/` directory. `CONTRIBUTING.md` ("Adding a package") says which mechanism to use, which list maps to which preset, and how versions are tracked.

Re-run `dfctl apply` to pick up the change: it installs what a list gained and, after a confirmation prompt, uninstalls what a list dropped. To skip a package on one machine only, add it to that machine's opt-out file instead — see "Presets and the Overlay" below.

=== Updating Configuration Files

. *Change Configs*: Edit the files directly in their `stow` packages (e.g., `~/.dotfiles/zsh/.zshrc` or `~/.dotfiles/claude-profiles/claude_work.json`).

. *Run `dfctl propose`*: This command will automatically add all changes (aborting first if `scripts/validate-no-machine-paths.sh` fails or `claude/.claude/settings.json` has uncommitted changes; use `/claude-settings-split` for the latter), commit them with a standard message, push the current branch (creating `backup/<timestamp>` when on `main`), and open a pull request if none exists. `main` is protected, so merge the PR once CI is green, then run `git switch main && git pull`.
+
[source,bash]
.Commit changes and open a PR.
----
dfctl propose
----
+
`dfctl install` and `dotfiles-backup save` are deprecated aliases for `apply` and `propose`; they print a notice and will be removed.

=== Stowing and Unstowing Packages

To manually manage packages, you can run `stow <package-name>` or `stow -D <package-name>` from the `~/.dotfiles` directory.

* `stow <package-name>`: Creates the symlinks for the package.
* `stow -D <package-name>`: Deletes the symlinks for the package.

[NOTE]
`dfctl apply` handles stowing automatically. This manual method is only for quick adjustments or troubleshooting.

Packages listed in `.stow-packages` are stowed unfolded (one symlink per file) so that new files appear without a restow.
`gradle` is the one exception and stays folded — `gradle/.gradle` is the live Gradle home, and unfolding its ~1.1M cache files would exhaust `stow` before it wrote anything.
`claude` is unfolded like the rest (rather than folded for convenience) specifically so the overlay below can also contribute files under it without two source directories fighting over one top-level symlink.
`dfctl` refuses to unfold any package over 1000 files rather than attempting it.

=== Claude Code Skills

Shareable Claude Code skills and commands live in a separate public repo, https://github.com/austek/ustekai-skills[austek/ustekai-skills], packaged as a Claude Code plugin marketplace named `ustekai-skills` (plugin keys read `<plugin>@ustekai-skills`) and referenced from `claude/.claude/settings.json`.
This repo carries no vendored skills or commands of its own.
Add a new skill there, not here.

== Presets and the Overlay

=== Presets

A *preset* is a manifest at `presets/<name>.json` that lists which package files (from `packages/`) to install, any backend-specific package-name overrides (e.g. for `apt`), and which `claude-profiles/*.json` file supplies Claude Code settings. This repo ships three — `work`, `personal`, `homelab` — and the set is extensible: drop in a new `presets/<name>.json` to add a machine type, no code changes required.

Running `dfctl apply --preset <name>` installs the preset's package files plus the overlay's extras, minus the names in `~/.config/dotfiles/packages/<name>.txt`. That file holds only your opt-outs for this machine, one name per line, under the header `# dotfiles-setup opt-outs v1`. It is yours to hand-edit; the install never regenerates it. A missing file means no opt-outs.

The install records what it applied in `~/.config/dotfiles/state.json`. On the next run, a package that is no longer wanted and is still installed — because a list dropped it or you opted out of it — is listed and removed only after you confirm. `--prune` confirms without asking; a non-interactive run without it, or a declined prompt, removes nothing and asks again next time; `--dry-run` only lists. Ctrl-C at the prompt stops the install before any step. apt packages, Zoom and GitHub pins are removed through apt, only in the system stage (`--no-system` skips them with a warning), never cascading to other packages and never with `autoremove`. A package that moved to another manager, e.g. a pin now listed as an apt package, is kept. Other vendor-script installs (e.g. SDKMAN, nvm) are reported for manual removal. Removals that did not happen are listed and offered again next run. Any Flatpak install failure, or a saved overlay that is now missing, skips all removals for that run; an overlay found at a new path is used and its path saved.

After a successful install, switching presets moves the other presets' opt-out files to `~/.local/state/dotfiles/package-backups/<timestamp>/`. A full package list from an older version of this repo is converted once to an opt-out file, with a backup in the same place; installed packages that only that old list named are offered for removal on that run.

=== The Overlay

An optional sibling clone at `~/.dotfiles-overlay` (or a path given via `DOTFILES_OVERLAY_ROOT`) is auto-detected and layered on top of this public repo for anything that shouldn't live here. If you already have such a repo, bootstrap it with:

[source,bash]
----
dfctl overlay clone --repo git@github.com:you/dotfiles-overlay.git
----

This clones straight to `~/.dotfiles-overlay` (override with `--dest`) and refuses to run if that path already exists, so it never overwrites an existing clone or unrelated directory — update an existing clone with a plain `git -C ~/.dotfiles-overlay pull` instead. Once cloned, the next `dfctl apply --preset <name>` auto-detects it and layers in everything below:

* *Full git identity, no prompt* — if `~/.dotfiles-overlay/git/gitconfig.local` exists, `dfctl apply` symlinks `~/.gitconfig.local` straight to it instead of interactively prompting for name/email/signing key. Use `~` (not an absolute `/home/<user>` path) for the signing key so the same overlay repo stays portable across your own machines.
* *Work-remote override* — `~/.dotfiles-overlay/git/gitconfig-work` is conditionally included by `git/.gitconfig` on Collibra remotes (see "Git Configuration" above).
* *Extra packages* — `~/.dotfiles-overlay/packages/<preset>_extra.txt` is unioned into the resolved package list for that preset; opt-outs in `~/.config/dotfiles/packages/<name>.txt` apply to these names too.
* *Extra Claude settings* — `~/.dotfiles-overlay/claude-profiles/<preset>.json` is deep-merged into the generated `~/.claude/settings.json` last, over this repo's own `claude-profiles/<preset>.json`; lists union.
* *Overlay stowed files* — after stowing this repo's own `.stow-packages`, `dfctl apply` also reads `~/.dotfiles-overlay/.stow-packages` and stows those packages (unfolded, from the overlay repo) onto `$HOME` too. An overlay file wins over a public one at the same path, not just adding new ones: the public stow skips paths the overlay owns, and `dfctl apply` clears the public symlink there before stowing the overlay — e.g. an overlay `claude/.claude/CLAUDE.md` with org-specific instructions this machine's user isn't free to publish replaces this repo's generic one, while `claude/.claude/skills/*` (overlay-only skill directories) and `local/.local/bin/*` scripts just add alongside it. Packages that belong to one preset go in `~/.dotfiles-overlay/.stow-packages.<preset>` (e.g. `.stow-packages.work`): that preset stows them, and every other preset runs `stow --delete` on them so links from an earlier install disappear.

If `~/.dotfiles-overlay` doesn't exist, none of the above applies — a plain fork of this repo runs off its public defaults alone.

The overlay used to be called the private overlay. A checkout still at `~/.dotfiles-private` keeps working, and `dfctl apply` moves it to `~/.dotfiles-overlay` for you: it unstows the overlay's packages from the old path, moves the directory, repairs the checkout's linked git worktrees and `~/.gitconfig.local`, and restows the packages. When both paths exist it uses the new one, unstows the old one's links and warns. It leaves the checkout alone when `DOTFILES_OVERLAY_ROOT` or `DOTFILES_PRIVATE_ROOT` pins its location (the legacy variable also warns), and it refuses a linked worktree. `DOTFILES_PRIVATE_ROOT` and `dfctl private clone` still work and print a deprecation notice; update your own repo's remote with `git remote set-url origin <new-url>` if you rename it on GitHub.
