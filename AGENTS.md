# AI Assistant Guidelines for Dotfiles

This document provides guidelines for AI assistants (like Gemini, Claude, or GitHub Copilot) when contributing to or modifying this repository.

## Repository Context
- This repository contains personal configuration files (dotfiles) for an Ubuntu-based development environment.
- It is designed to be automated, preset-aware, and easily deployed on new machines.
- The core architecture relies on **GNU Stow** to manage symlinks and the `dfctl` Python CLI (`bin/dfctl`, implemented by the `bin/dotfiles_setup/` package, which keeps its name because a package at `bin/dfctl/` would collide with the script) to orchestrate the installation. The old name `dotfiles-setup` is a deprecated shim (`bin/dotfiles-setup`) that prints a notice and runs `dfctl`; the on-disk names `~/.dotfiles-setup-rollback.log`, the `# dotfiles-setup opt-outs v1` header and the `~/.cache/dotfiles-setup` download cache keep the old spelling so existing machines are not orphaned. There is no installer shell script: every step lives in a Python module, and `install_flow.py` lists them in run order.

## Architecture & Design Principles

### 1. Package Management (Strict Rule)
- **NEVER** suggest or use `apt-get install` directly to add applications.
- To add or remove applications, update the text files in the `packages/` directory of the Workspace clone (`~/Workspace/austek/dotfiles/packages/`).
- GUI apps that Flathub ships (`flatpak_desktop.txt`, `flatpak_work.txt`) are written as `flatpak:<app-id>` and installed user-level, without sudo, by `flatpak.py`. Apt skips these entries. `DOTFILES_SKIP_FLATPAK=1` makes `flatpak.py` skip the whole step with an info line and no failures; `e2e/compose.yaml` sets it because Flatpak's sandbox and D-Bus do not run in the CI container. Other CLI and sandbox-hostile apps stay on apt, `.deb` or vendor scripts.
- `dfctl apply --upgrade` also runs `apt-get dist-upgrade` and `flatpak update`, and forces the system stage. Without it, the install only reports how many apt packages are upgradable. A pinned `.deb` in `github_bins.txt` is installed when it is absent or older than the pin (`dpkg --compare-versions`); a newer installed version is logged ("<name> v<installed> is newer than the pin v<pin>; leaving it") and left alone, and `system_check` does not count it as pending. A version dpkg cannot compare is also left, with a log line. An epoch prefix and a `-` or `+` revision suffix are ignored, so an installed `2.0-1` counts as the pin `2.0`. Release installers (`release_installers.py`) install a pinned version whose URL digest is in `packages/checksums.txt`. Each pin is one line of `packages/release_specs.json` (`version`, plus `url` and `cache_key` templates over `{version}`); the install steps for zoom, jetbrains-toolbox and awscli stay in code, keyed by `package`; awscli runs `aws/install -i ~/.local/aws-cli -b ~/.local/bin --update` as the user (no sudo, counted as installed when `~/.local/bin/aws` is an executable file, not touched by `--upgrade`); when the installer exits 0 without creating the `aws` link (a pinned tree that already exists), the step links it to the tree's `v2/current/bin/aws` (else the newest `v2/<version>/bin/aws`), considering only executable candidates, and fails with "left no aws executable" when there is none; when the tree has an executable but a non-executable regular file sits at `~/.local/bin/aws`, the file is kept and the step fails with a "Cannot restore the aws command" conflict error. When `~/.local/aws-cli` did not exist it records `TREE_INSTALLED:<root>|<link>|<dev>:<ino>`, which always names the `aws` link, whether or not that link was there before, and the tree's device and inode taken after the install; rollback checks the tree's identity first: when its current device and inode differ from the record, or the entry has only the older two fields, both the tree and the link stay with "Kept <root> and <link>: ownership could not be verified."; otherwise it removes the link only while it still resolves into the tree and then the tree, keeping both when the link was retargeted or is a regular file. When the tree already existed, nothing names it, and only the links are recorded as `LINK_INSTALLED:<root>|<link>`: `aws` when it was absent before and present after, and `~/.local/bin/aws_completer` under the same condition (a dangling symlink counts as absent, so a relinked one is recorded), each removed on rollback only while it resolves into the tree; istioctl is a plain `binary` spec like the others; and a spec with a `binary` field installs that binary as the user into `~/.local/bin` (mode 0755, replaced atomically, no sudo; the `install_user_binaries` step in the user stage, which fails and offers rollback when `~/.local/bin` cannot be created and creates none on a non-x86_64 machine; kind `binary` is a raw, non-archived download installed under that name; the binary counts as installed only when `~/.local/bin/<binary>` is an executable file (a mode 0644 file is replaced by the install, and by `--upgrade` for `chip`, with a mode 0755 copy; `report_stale_copies` ignores it too), whatever else is on `PATH`; it records `BIN_INSTALLED:<path>|<sha256>` for rollback, which removes the file only when its digest still matches (rollback first moves the file into a fresh `.<name>.rollback-XXXX` directory beside it, so a file that appears at the old name meanwhile is never touched, hashes the moved file, deletes it with its directory on a match, and otherwise links it back without overwriting a newer file, keeping the directory and logging its path when it cannot; an unreadable file is put back; a symlink entry is moved and checked the same way; only the recorded kind is held, a regular file for `BIN_INSTALLED` and a symlink for link entries, and anything else is left untouched with "Kept <path>: it is not a <kind>."; a held file that cannot be deleted is put back and the aws tree stays, while a holding directory that cannot be removed is only a warning), and `DIR_CREATED` when it created `~/.local/bin`; `--upgrade` replaces an installed `chip` whose `chip --version` is older than the pin; `chip` is not in any repo preset list, the overlay opts in with `packages/<preset>_extra.txt`). `~/.local/bin` precedes `/usr/local/bin` on `PATH` (`zsh/.zshenv`, and the foothold unit's `PATH_DIRS`), so a copy an earlier version put in `/usr/local/bin` is shadowed, not removed. `~/bin` precedes `~/.local/bin`, so a hand-installed `~/bin/<binary>` shadows the new copy. The `report_stale_copies` step reports such copies (see "User-Level Executables"). The `link_user_tools` step (user stage, after `install_user_binaries`) symlinks `jetbrains-toolbox` (`~/.local/share/JetBrains/Toolbox/bin/jetbrains-toolbox`) and `sonar` (`~/.local/share/sonarqube-cli/bin/sonar`) into `~/.local/bin` once their installers have run, so `zsh/.zshenv` carries no PATH entry for either `bin` directory (the Toolbox `scripts` entry stays: it holds launchers a symlink does not cover). A link is replaced only when it is a symlink; a regular file or directory under that name is warned about and kept (resolve the warning, then re-run `dfctl apply`), a link creation that fails warns the same way, and the step never fails, so apply can still succeed; it creates `~/.local/bin` when it links a binary that exists, and a link it cannot make warns with the consequence (for `sonar`, "`sonar` on PATH is not the SonarQube CLI"). A new link records `LINK_INSTALLED:<tool dir>|<link>`, whose rollback removes it only while it still points into that directory. A malformed file fails the import, and the `.deb` helpers are in `deb_helpers.py`. To bump one, change its `version` in that file, change the matching URL in `packages/checksums.txt`, then run `mise run pin <url substring>` (`pin` never adds a URL). Renovate bumps the pin and the `checksums.txt` URL together for lazydocker, istioctl, AWS CLI and cargo-deny and for zizmor and mcp-grafana (the `version` field of their `release_specs.json` lines), but cannot recompute the digest, so run `mise run pin <url substring>` on its PR. It bumps no version for zoom or JetBrains Toolbox, and bumps Antigravity's `PINNED_BUILD` without that build's `checksums.txt` URL, so those need the same follow-up edits by hand. `--upgrade` installs the pinned `zoom` `.deb` only when the installed version is older (`dpkg --compare-versions`), never a downgrade. Slack is not a `.deb` install: `flatpak_work.txt` lists `flatpak:com.slack.Slack`, which `flatpak update` upgrades.
- Available package lists include: `apt_common.txt` (all presets, headless-safe), `apt_desktop.txt` (GUI packages, pulled in by `work`/`personal` only), `apt_rust.txt` (Rust tooling shared by `personal` and `homelab`; `cargo-deny` installs from its `release_specs.json` musl binary, `cargo-audit` from `cargo install`), `apt_k8s.txt` (age, flux, helm, kubeconform, sops for every preset; `kubectl` is in `apt_common.txt`; every name but `age` installs from its `release_specs.json` pin, `kubectl` included), `apt_work.txt`, `apt_personal.txt`, `apt_homelab.txt`, and `github_bins.txt`.
- `apt_packages.py` downloads and installs the `.deb` packages from GitHub releases listed in `github_bins.txt`.

### 2. Snap-Free Environment
- This is a strictly Snap-Free edition.
- `snapd` is automatically removed and blocked via an `apt` preference file in the `system/` package. Do not write scripts that rely on snap packages.

### 3. Preset-Aware Setup
- The setup is preset-aware. `dfctl apply` requires `--preset` only on a machine with no saved preset; otherwise it reuses the saved one, and an explicit `--preset` overrides and replaces it.
- It builds configuration files based on the chosen preset.
- Per-preset Claude Code settings are stored in `~/.dotfiles/claude-profiles/` and merged into the generated `~/.claude/settings.json` (see section 5); a machine has one preset, so there are no per-session profiles, wrapper or aliases, and an install removes the ones an older version generated. The one exception is the `claude` zsh function (`zsh/.config/zsh/functions/claude`; `_claude_tmux` and `_claude_with` are its private helpers), which takes `--account <name>`, `--burst` and `--with <names>` before a literal `--` and passes everything else to Claude Code. An account other than `main` runs with `CLAUDE_CONFIG_DIR=~/.claude-<name>` (`[a-z0-9][a-z0-9_-]*`, `main` reserved), made only by `claude-account create` (`--account <unknown>` fails with a pointer to it) and kept in a manifest at `~/.config/dotfiles/claude-accounts/<name>.json` (outside `~/.claude`, whose entries `claude-account-link` links into every account) with `telemetry`, `labels`, `otel_account` and `api_key_env`; `claude-account update|rename|ls` manage it. A rename moves the dir, the manifest and the saved `--with` names, keeps the old OTel account label unless `--relabel`, and refuses a foothold account of the saved preset or an account with a running tmux session. `api_key_env` names a `secrets.env` variable that `claude` exports as `ANTHROPIC_API_KEY` in a subshell, never on a command line or in a manifest. On each launch `bin/claude-account-link <name>` (`bin/claude-burst-link` is `claude-account-link burst`, which the burst foothold also runs) symlinks every `~/.claude` entry except `.credentials.json`, `.claude.json` and `backups` into that dir, so the account shares the generated settings, sessions and plugins and keeps only its own login and `.claude.json`. It needs no install step and no profile file; never exclude `settings.json` from it or give it a `--settings` layer. `--with` runs `_claude_with` with the account's env exported and saves its names under `~/.local/state/dotfiles/claude-with/<account>` (outside the config dir, which burst would share); a bare `--with` reads them back. On the `personal` and `homelab` presets `claude` also exports Claude Code's OTel env (`claude-otel-env <account>`, a zsh wrapper over `bin/claude-otel-env`: host from the saved preset, machine from the hostname, account name, project from the git root) to the collector, `CLAUDE_OTEL_ENDPOINT` overriding the address; the foothold units do not go through `claude`, so `claude-foothold-launch` sets `CLAUDE_OTEL_ACCOUNT` and `claude-env-load` exports the same env after `secrets.env` (a variable `secrets.env` sets wins, and `CLAUDE_OTEL_ENDPOINT` there is honoured), with `project` fixed to the start directory's git root or basename for the life of the pane; the `claude-remote` skill sets `CLAUDE_OTEL_ACCOUNT` the same way, from `--config-dir` or else the inherited `CLAUDE_CONFIG_DIR` (`main` when neither is set, `<name>` when the directory's basename is `.claude-<name>`, whatever its parent; any other directory omits the assignment, so a `secrets.env` value still applies), and a session started from inside a foothold pane inherits that pane's labels. See "Presets and Portability" below for how a preset's package list is resolved and how per-machine opt-outs work.

### 4. Apt Repositories
- Third-party `apt` repositories are declaratively managed using `.sources` files within the `apt/` package.
- The setup script handles securely downloading the latest GPG keys.
- An unreachable apt source does not stop the install. A signing-key download, PPA add or 1Password policy download is retried 3 times (10 s, 20 s apart); after that the source and the packages that need it (`SystemContext.skipped`) are left out of the run: its source file is not stowed or rendered, `install_packages` leaves the packages out, and `report_skipped_sources` lists them at the end. An interactive run asks first (`Skip <source> and continue without <packages>? [Y/n]`, where `n` or EOF stops the step as before); a non-interactive run skips with a warning. Other failures (gpg, stow, `apt-get`) still stop the install. A skipped source keeps its previously rendered `.sources` file, and the packages stay in the wanted list, so the next run retries them. `add-apt-repository` runs under `sudo timeout 45` with `--no-update` (the cache refresh belongs to `install_packages`) because `launchpadlib` retries a dead connection without limit; each failed attempt prints one line (the last line of its output, e.g. `TimeoutError: ...`, or `timed out`) and the full output goes to syslog.
- Every `Logger` message (`info`, `success`, `banner`, `step`, `warn`, `error`, dry-run notices), at any verbosity, plus the output of a failed `quiet_run` command (only its exit status at `-vv`, where the output streams to the terminal), is also written to syslog under the tag `dfctl` (`journalctl -t dfctl`, and `/var/log/syslog` where rsyslog runs). Tests stub syslog in `conftest.py`; new output code must go through `Logger`, not `print`, to be logged.
- A source the preset no longer selects loses its stowed link: stow applies `--ignore` when unstowing too, so `stow_apt_source_files` first moves each owned link (a symlink into `apt/`) of a deselected `SOURCE_FILES` entry into `/var/backups/dotfiles-stow` and records `FILE_BACKUP` for rollback. A regular file or a link elsewhere is left alone.
- A non-dry-run install also writes a transcript to `~/.local/state/dotfiles/logs/install-<timestamp>.log` (mode 0600 in a 0700 directory, newest 10 kept; `transcript.py`): every `Logger` message, plus each command run through `Tooling.run` with its exit code and the stdout/stderr it captured. Input given to a command is never recorded, and output a command sends straight to the terminal is not seen. A transcript that cannot be written never fails the install.

### 5. Claude Code Skills
- Shareable Claude Code skills and commands live in a separate public marketplace repo, [austek/ustekai-skills](https://github.com/austek/ustekai-skills) (marketplace name `ustekai-skills`, so plugin keys read `<plugin>@ustekai-skills`), referenced from `claude/.claude/settings.json`'s `extraKnownMarketplaces`/`enabledPlugins`.
- This repo carries no vendored skills or commands of its own.
- `~/.claude/settings.json` is generated, not stowed: `dfctl apply` merges `claude/.claude/settings.json` (base), the preset's `claude-profiles/<file>.json`, the overlay's `claude-settings/settings.json` and the overlay's `claude-profiles/<preset>.json`, later layers winning (objects deep-merge, lists union), and backs up a differing existing file to `settings.json.bak-<timestamp>` (`-1`, `-2` on a name clash). The swap is atomic (`bin/dotfiles_setup/fsutil.py`): the new text is written to a temp file beside the target, fsynced, given the old file's mode (0600 for a new file or a replaced symlink), then `os.replace`d, so `settings.json` is never absent or half-written; the backup is a hard link (a copy where links fail) made before the replace. The baseline is written the same way after the settings file. A crash between the two leaves new settings with an old or missing baseline, which reads as drift: re-run with `--accept-drift` to recover. Edit the base or the overlay, never the generated file. Claude Code copies `env` values literally, so install replaces `$HOME`, `${HOME}` and a leading `~` in `env` string values with the machine's home; write portable values there, never an absolute home path. Install records what it wrote in `~/.config/dotfiles/settings.last-generated.json` and, before any other step, compares the live file against it: hand edits since the last install print a diff and stop the install (exit 3); `--accept-drift` overwrites them, and `--dry-run` prints the diff and continues. With no recorded baseline (first run) the check is skipped.
- The `cozempic@cozempic` plugin supplies cozempic's hooks, so the base settings carry none. `COZEMPIC_NO_GLOBAL_INIT=1` (base `env`, and set on the installer's own `cozempic` calls in `claude_tools.py`) keeps cozempic from writing its own hooks back into the generated settings, which would duplicate them and trip the drift check. `COZEMPIC_NO_AUTO_INIT=1` (base `env`) stops it from creating a project-level `.claude/settings.json` with duplicate hooks in whatever directory a session starts in, such as an untracked `~/.dotfiles/.claude/` that `dfctl propose` would commit.
- To add a new skill, author it in `austek/ustekai-skills`, not here.
- `dfctl apply` ends by syncing Claude Code with the generated `settings.json` (`bin/dotfiles_setup/claude_plugins.py`), in this order: uninstall plugins from managed marketplaces that settings do not enable, remove legacy marketplaces, add declared marketplaces, refresh marketplaces, install enabled user-scope plugins, update the user-scope plugins that were already installed. Managed marketplaces are those in `extraKnownMarketplaces` plus `LEGACY_MARKETPLACES`. Uninstalls and marketplace adds/removes touch only managed marketplaces; the refresh and update steps cover all of them. Uninstalls and legacy removals are skipped when settings enable no plugin. `--dry-run` prints each planned step (it still runs the read-only `claude plugin list` commands). Failures warn and never fail the install; Claude Code needs a restart to apply changes.
- When a marketplace is renamed, add its old name to `LEGACY_MARKETPLACES`; Claude Code rejects adding a marketplace whose name collides with a registered one, so the installer removes the old one before adding the new one.

### 6. Claude Remote Foothold
- A preset's `footholds` list (`presets/<name>.json`; anything but a list of names fails the preset load) names the accounts that get a boot-time Remote Control session: `main` and `burst`. `personal` and `homelab` list both; `work` lists none. `dfctl apply` ends by syncing them (`foothold.sync_footholds` in `bin/dotfiles_setup/foothold.py`): it installs `~/.config/systemd/user/claude-foothold.service` for `main` and `claude-foothold-burst.service` for `burst`, each starting a tmux session of the same name (`claude-foothold`, `claude-foothold-burst`), and retires the unit of every account the preset does not list. It also runs `loginctl enable-linger` so the units start at boot without a login, then `systemctl --user enable --now`.
- The Remote Control session is named after the machine: `%H` for `main` and `%H-burst` for `burst`, which systemd expands to the hostname when the unit starts, so a renamed machine needs no rewrite. The burst unit is skipped, with a warning, until `~/.claude-burst/.credentials.json` exists: log in once with `claude --burst` and re-run the install.
- The unit probes `api.anthropic.com` before launching; without that wait, Remote Control fails session creation at boot because the link gains carrier before DNS works. Its `PATH` includes `~/.local/bin`, where the `link_user_tools` step symlinks `sonar` once the SonarQube install has produced it, so the SonarQube plugin finds it. The tmux pane runs `bin/claude-foothold-launch <name> [burst]`, which `exec`s `bin/claude-env-load bin/claude-pane-loop claude …`. `claude-env-load` loads `~/.config/dotfiles/secrets.env` as data and puts the newest nvm node on `PATH` before running its command, and only when the file is a regular file owned by the user that neither group nor other can access (it warns on stderr otherwise); other launchers (the `claude-remote` skill) wrap `claude` in it too. `claude-pane-loop` keeps the pane open briefly after claude exits so a typed `--resume` line can restart it. The unit has no `EnvironmentFile=`: systemd would read the file whatever its mode, and `claude-env-load` is the single loader; every var in that file reaches Claude. With `burst` it first runs `bin/claude-burst-link` and passes `CLAUDE_CONFIG_DIR` through `claude-pane-loop` as an `env` prefix, so a resumed claude stays on the burst account.
- It is skipped when `systemctl`, `tmux` or `curl` is missing, and failures warn without failing the install. A unit is rewritten only when its content changes; an already-running session is not restarted, so run `dfctl foothold restart` (restarts every installed foothold unit through `systemd-run --user --wait`, so the restart runs outside every foothold session and still restarts all of them when run from inside one it ends, after a connectivity probe and a rewrite of a stale unit, whose `ExecStop` ends the old tmux session; safe to run from inside the session; supports `--dry-run`) to pick up changes.
- Units used to be named after the preset (`claude-foothold-<preset>.service`). `retire_legacy_footholds` finds every such unit by name, whichever preset wrote it, disables it, kills its tmux session and removes its unit file, once the `main` unit is installed; for a preset without `main`, once every unit it lists is installed, which is at once when it lists none.

### 7. User-Level Executables
- Every installer that writes a user-level executable puts it in `~/.local/bin`, or symlinks it into that directory (`fsutil.link_executable`: temp symlink plus `os.replace`, idempotent, replaces only a symlink, and returns `Err` without touching a regular file or directory). `release_installers.user_bin_dir` is the single resolver for the path; code outside that module never spells it.
- Exceptions: files dpkg owns (apt, `github_bins.txt`, zoom), Flatpak exports, and toolchains that manage themselves (SDKMAN, nvm, rustup and cargo). Antigravity is a root-owned `/opt` install with a setuid sandbox; it runs in the system stage (`install_system_tools`, counted by `system_check` while its build is absent or not the pinned one), so `--no-system` skips it. The allowlist for new executables under `$HOME` is `~/.local/bin`, `~/.sdkman`, `~/.nvm`, `~/.cargo`, `~/.oh-my-zsh`, `~/.local/aws-cli` and `~/.local/share/<tool>/`.
- One list holds every PATH directory: `packages/path_dirs.txt` (one `~/…` or absolute directory per line, `#` comments, order is precedence, first duplicate wins) plus the overlay's optional `packages/path_dirs_extra.txt`, appended after it. `zsh/.zshenv` reads both files directly with zsh builtins (no subprocess); `dfctl apply` renders the same list into the generated `~/.claude/settings.json` `env.PATH` (`claude_settings._merged_claude_settings`) and the foothold unit's `Environment="PATH=…"` (`foothold.render_unit`), via `path_dirs.load`, `for_env` and `for_systemd`. `~/.dotfiles/bin`, `~/bin` and `~/.local/bin` come first, so a same-named copy in an earlier directory shadows the managed one. A malformed or missing base file stops `dfctl apply` and `dfctl foothold restart` with exit code 2; `.zshenv` falls back to those three directories when the base file is unreadable. `tests/test_path_dirs_invariant.py` fails when a directory dfctl installs into is missing from the list, or when a consumer grows its own copy.
- The `sonar` and Toolbox `bin` directories are not on the list; their `~/.local/bin` links make them reachable. The links exist only after the next successful `dfctl apply`.
- `tests/test_bin_policy.py` runs each user-level installer against a temporary home and fails on a new executable or symlink outside the allowlist; the AWS installer fake honours `-i` and `-b` and writes under the home when a flag is missing. A source scan (AST-based, every `.py` file under `bin/dotfiles_setup/`) fails on any string literal that is `sudo`, starts with `sudo`, or has `sudo [options] install|cp|mv|ln|tee|rsync` inside it (so `bash -c` strings and f-string literals count), and on the names `sudo` and `_sudo`, in a module outside `PRIVILEGED_MODULES` in that test. Each exempt module declares the sudo verbs it may run (for example `apt_packages`: rm, apt-get, dpkg), and the scan fails on any other verb there, on a declared verb the module no longer uses, and on a `sudo <write verb>` string; the verbs include those inside shell strings (`sh -c`, `bash -c`: a `sudo <verb>`, optionally written as an absolute `.../sudo` path, at the start of a line or after a newline, `;`, `&`, `|`, `(`, a backtick, `$(` or one of the commands `if`, `then`, `do`, `else`, `exec`, `xargs`, `env`, `time`, `nohup`, `eval`; options that take a value (`-u user`, and `-g`, `-h`, `-p`, `-C`, `-r`, `-t`, `-T`, `-U`, `-D`, `-R`) are skipped, so `sudo -u root chmod` reads as `chmod`, and prose such as "needs sudo access" is not read as a verb); a splatted or bare prefix counts as the verb `*`, declared only by `antigravity.py` and `rollback.py`. The scan sees literals and names only: a command assembled from pieces or read from data escapes it. Another test fails when a module spells the user bin dir outside `release_installers.py`: a whitespace-free literal containing `.local/bin` (`".local/bin"`, `"~/.local/bin"`, `"$HOME/.local/bin"`, an f-string tail), or `.local` and `bin` as consecutive parts of a `/` join, `os.path.join`, `joinpath` or `Path(...)` call. The one other exception is `foothold.py`, whose `%h/.local/bin` is a systemd specifier that systemd expands in the unit file, so no `Tooling` exists to resolve it. A new installer that needs sudo or another location extends those tables with its reason, in the same change.
- The `report_stale_copies` step (user stage, after `configure_claude_tools`; `stale_copies.py`) checks the binaries dfctl places in `~/.local/bin`: the wanted pinned release binaries (including istioctl and `aws`), `jetbrains-toolbox`, `sonar`, wanted uv, ruff, auditr, cargo-deny, cargo-audit and coderabbit, and always rtk and cozempic. For each it checks `~/.dotfiles/bin`, `~/bin` and `/usr/local/bin` for a same-named file that resolves to a different file, logs one info line per copy ("precedes ... and shadows it; remove it manually" for the two user directories, "is now shadowed by ...; remove it with sudo when convenient" for `/usr/local/bin` only while that directory is on the process's `PATH`, else the neutral "also exists; it is not on PATH here"; the two user directories keep the `.zshenv`-order wording whatever `PATH` holds), skips same-file symlinks, directories and broken symlinks, and deletes nothing.

## Presets and Portability
- Presets are manifests at `presets/<name>.json` (this repo ships `work`, `personal`, `homelab`); each lists which `packages/` files to install, which `claude-profiles/*.json` supplies Claude Code settings and which accounts get a foothold (`footholds`). Add a machine type by dropping in a new `presets/<name>.json`, not by editing code.
- `~/.config/dotfiles/packages/<preset>.txt` holds only the user's opt-outs, one name per line, under the header `# dotfiles-setup opt-outs v1`. Wanted packages = repo list + overlay `_extra.txt` + `packages/github_bins.txt` pins (`github:<user>/<repo>`) − opt-outs. The user hand-edits it; never suggest deleting or regenerating it.
- Names in the last applied list in `state.json` but absent from wanted are uninstalled after a confirmation prompt: names the repo or overlay drop, and names the user opts out of while they are installed (adding an installed package to the opt-out file offers its removal). The prompt lists only entries still installed, plus manual entries; with nothing installed it does not ask. EOF or any answer but y/yes declines with a warning; Ctrl-C exits 130 before any step. `--prune` approves non-interactively; a non-interactive run without it, or a declined prompt, removes nothing and keeps the names in the applied list while still installed; `--dry-run` only lists them. An approved removal that did not happen is warned about and offered again next run. When `state.json` records an overlay root and no overlay is found now, the run skips all removals with a warning; an overlay found at a different path is used and its path saved.
- apt packages go through a simulation-checked `apt-get remove` in the system stage (`remove_apt_packages` is in `SYSTEM_STEPS`; when the stage does not run, the run warns and removes none): never `autoremove`, never a removal that cascades to other packages. An entry whose dpkg package a wanted entry still installs (e.g. a pin now listed as an apt package) is kept and never offered. Flatpak apps go through `flatpak uninstall --user`. The `.deb`-backed custom entry `zoom` (`DPKG_BACKED_CUSTOM`) is removed the same way when dpkg reports it installed. Each `packages/github_bins.txt` pin is an entry `github:<user>/<repo>` (its dpkg package is the repo basename, so a pin whose package name differs is dropped silently); opting out of a pin skips its install and removes the installed `.deb`. Their undo is `DEB_REMOVED`, which only warns to reinstall manually. Every other vendor-script entry (`CUSTOM_INSTALL_PACKAGES`) is reported once, never removed. Any Flatpak install failure skips all removals.
- Only the saved preset's opt-out file exists: after a successful, non-dry run, other presets' files are moved to `~/.local/state/dotfiles/package-backups/<stamp>/`. A legacy forked file (a full package list) is converted once to an opt-out file, with a backup in the same directory: only while `state.json` lacks `optouts_migrated: true` and the file has no header line anywhere. Every saved install sets `optouts_migrated` unless writing the conversion failed, which fails the run and leaves the file legacy for the next run to retry; afterwards a headerless file is read as opt-outs with a warning. The opt-outs the conversion creates are never pending removals on that run, while installed entries only the old fork named (e.g. an apt `slack-desktop`) are offered for removal. Preserve these rules in any change that touches package planning.
- An optional sibling clone at `~/.dotfiles-overlay` (or `$DOTFILES_OVERLAY_ROOT`) is auto-detected and layered on top of this public repo: `git/gitconfig.local` for full git identity (name/email/signing key — see below), `git/gitconfig-work` for a work-remote identity override, `packages/<preset>_extra.txt` for extra packages, `claude-profiles/<preset>.json` for extra Claude settings merged over this repo's own, and its own `.stow-packages` for stowed files (e.g. Collibra-specific `claude`/`local` content), unfolded and stowed after the public packages (the public stow ignores paths the overlay owns and the public symlink there is cleared first) so an overlay file at the same path as a public one (e.g. an org-specific `claude/.claude/CLAUDE.md`) wins rather than conflicting. An overlay `CLAUDE.md` that shadows the public one should start with `@~/.dotfiles/claude/.claude/CLAUDE.md` and add only org-specific rules, so the generic ones keep living here. A package listed in `.stow-packages.<preset>` is stowed for that preset only; the other presets `stow --delete` it, so links from an earlier install go away. It is a separate repo — never assume it exists, and never put its content in this one.
- If the overlay provides `git/gitconfig.local`, `dfctl apply` symlinks `~/.gitconfig.local` to it and skips the interactive git-identity prompt entirely (`identity.ensure_git_identity`'s `overlay_root` param). Write paths in that file (e.g. the signing key) as `~/...`, never an absolute `/home/<user>/...`, so the same overlay repo works unmodified across the user's own machines.
- `dfctl overlay clone --repo <url>` bootstraps that sibling clone (default dest `~/.dotfiles-overlay`, override with `--dest`) instead of a manual `git clone`. It refuses to run if the destination already exists — use `git -C <dest> pull` to update an existing clone.
- The overlay used to be the "private overlay" (`~/.dotfiles-private`, `$DOTFILES_PRIVATE_ROOT`, `dfctl private clone`), and those names still resolve: `find_overlay_root` (`overlay.py`) prefers `$DOTFILES_OVERLAY_ROOT`, then `$DOTFILES_PRIVATE_ROOT`, then `~/.dotfiles-overlay`, `~/.dotfiles-private` and the local overlay; an override variable that points at a missing path means no overlay. `dfctl apply` runs `overlay_migrate.migrate_legacy_overlay` right after resolving the preset: when only `~/.dotfiles-private` exists and no override variable is set, it calls `overlay_migrate.relocate`: `stow --delete` for every package directory named in `.stow-packages` and `.stow-packages.<preset>` (a name without a directory is skipped, because stow refuses the whole call over it, and editor backups are not read), the rename to `~/.dotfiles-overlay`, `git worktree repair` there (linked worktrees keep an absolute path to the checkout), a repoint of `~/.gitconfig.local` when it links into the old path, and an immediate `stow --restow --no-folding` from the new path, so a later failing step never leaves the overlay unlinked. It records `OVERLAY_MOVED:<old>|<new>`, and rollback runs `relocate` the other way. If the unstow fails nothing moves; if the move fails it restows from the old path. When both paths exist the new one wins and the old one's links are unstowed, with a warning; an override variable leaves the checkout alone, and a linked worktree stops the run; `--dry-run` only reports (it says a worktree would be refused). `git/.gitconfig` lists both `gitconfig-work` paths because git ignores a missing include, the legacy one first so the overlay's values win when both exist (later includes take precedence). Without `stow` installed (exit status 127) the migration defers: nothing moves, the legacy path keeps working and a later apply moves it. The `STOW_PRIVATE` and `UNSTOW_PRIVATE` rollback entry names keep their spelling because rollback logs on disk use them. `dfctl private clone` is a deprecated alias of `dfctl overlay clone`; remove the legacy names one release after this lands. The overlay's GitHub repo is `austek/dotfiles-overlay`, and the old `dotfiles-private` URL redirects to it.

## Shell & Environment Standards

### Zsh Configuration
- Custom Zsh functions must be stored in `~/.config/zsh/functions`.
- They are efficiently loaded using `fpath` and `autoload`.
- zsh's completion dump (`~/.zcompdump*`) is rebuilt only when the number of completion files changes, so a rename, or a changed `#compdef` line, that keeps the count equal leaves stale completers. `dfctl apply` therefore fingerprints the names and `#compdef` header lines of every `_*` file in `~/.config/zsh/completions` and `~/.oh-my-zsh/custom/completions`, the directories already on `fpath` when oh-my-zsh runs `compinit` (`zsh_cache.py`, run after the stow step; `~/.config/zsh/functions` is added later and is not watched) and removes `~/.zcompdump*` when the fingerprint, kept in `~/.local/state/dotfiles/zsh-completions.sha256`, changes or has no record yet. A dump it cannot remove, or a fingerprint it cannot record, only warns and is retried next run; `--dry-run` only reports. It cannot see a dump kept elsewhere through `$ZSH_COMPDUMP`. Open a new shell afterwards.
- `.zshrc` calls `dfctl-update-check` (`zsh/.config/zsh/functions/dfctl-update-check`, helpers in the `_dfctl_update_*` files beside it) once per interactive shell, after oh-my-zsh, the function autoload, `~/.zshrc.secret` and `secrets.env`, so a zstyle set in either of those files takes effect. It is modelled on oh-my-zsh's update prompt and needs only the function autoload, nothing else in `.zshrc`. Two zstyles tune it and the repo's `.zshrc` sets neither: `zstyle ':dfctl:update' mode ask|auto|reminder|disabled` (default `ask`, an unknown value counts as `ask`) and `zstyle ':dfctl:update' frequency <days>` (default 7, a non-numeric value counts as 7). It does nothing, silently, when the mode is `disabled`, stdin or stdout is not a tty, the stamp is younger than `frequency` days, or another shell holds the lock.
- The stamp is `${XDG_STATE_HOME:-~/.local/state}/dotfiles/update-check` (`LAST_EPOCH=<days since epoch>`); the lock is the `update-check.lock` directory beside it, and one older than an hour counts as stale and is reclaimed by a rename: the shell renames the directory to `update-check.lock.stale.<pid>.<time>` (`_dfctl_update_reclaim`), re-checks the age of the renamed directory and removes it, and only a shell whose rename moved a directory that is still old goes on to create the lock. The rename is atomic, but the age check before it is not: a rename that moved a lock another shell had just created moves it back when the name is free and fails; if a third shell took the name meanwhile, the fresh lock stays under its `.stale.` name and two shells can briefly hold the lock. A `.stale.*` directory older than an hour, left by a killed reclaim, is removed on the next reclaim. The lock holds an `owner` file with the holder's token (`$$.$EPOCHREALTIME`); a shell removes the lock on exit only while the file still holds its own token (`_dfctl_update_unlock`), so a shell whose stale lock was reclaimed does not remove the new holder's lock. The token is checked just before the removal, not atomically with it: a shell that reclaims the lock in that instant can still lose it. A lock without an `owner` file is reclaimed after an hour the same way. It is a plain reminder: it checks nothing for changes. With no stamp (the first shell), an unreadable or malformed one, or one dated in the future, it writes the stamp and stays silent. Once the stamp is `frequency` days old, `ask` prints how many whole days have passed and reads one key: `y` or `Y` updates, anything else (Enter included) writes the stamp, which snoozes the prompt for `frequency` days, and prints `Run dfctl apply --upgrade when ready`. `auto` prints the day count and updates at once. `reminder` only prints `[dfctl] It has been N days since the last dfctl apply or reminder. Run dfctl apply --upgrade when you are ready.` (N counts from the stamp, which a snooze also writes) and writes the stamp, so it repeats once per `frequency` days; it runs no pull or apply, shows no prompt and reads no key. Unlike oh-my-zsh's `reminder`, which leaves its stamp alone and so nags every shell until `omz update` runs, this one snoozes. In `ask` mode, keystrokes already waiting on the tty (`_dfctl_update_typed`, as oh-my-zsh's `has_typed_input`, needs `stty`; without it the prompt shows) make it print the same reminder line instead of the prompt, since the prompt would swallow them, and write the stamp, so it snoozes for `frequency` days; `auto` ignores pending input. Both reminder paths first print a clear-line sequence (`\r\e[0K`); it is sent only when stdout is a tty, which the check already requires. The update runs `git -C ~/.dotfiles pull --ff-only` when that checkout is on `main` (a failure warns and skips apply), then `dfctl apply --upgrade` (`dfctl` from `PATH`, else `~/.dotfiles/bin/dfctl`). The stamp is written after any attempt, successful or not, so the day count runs from the last apply, update attempt or reminder; a non-zero exit prints the code and the command to retry. A successful, non-dry-run `dfctl apply` (exit 0, after the state is saved) writes the same stamp (`update_stamp.py`, atomic; it creates the directory 0700 only when it is missing), so applying by hand resets the clock; a write failure only warns. Keep `tests/test_dfctl_update_check.py` and `tests/test_update_stamp.py` in step.
- The base `PATH` lives in `zsh/.zshenv`, not `.zshrc`, so non-interactive shells (IDE-launched agents) get it. Add a directory to `packages/path_dirs.txt`, never to a consumer; `typeset -U path` keeps entries unique and `path=( ${^path}(N-/) )` drops directories that do not exist. Use `path_prepend` / `path_append` only for additions in `.zshrc` (e.g. tool installers), never `export PATH=...`.

### No Machine-Specific Paths
- **Never** hardcode an absolute home directory (`/home/<user>`, `/Users/<user>`). Use `$HOME` or `~`, so the file works on every machine.
- Inside a JSON hook `command`, write `"$HOME/..."` with **double** quotes. Single quotes stop the shell expanding it, leaving a dead literal path.
- `~/.zshrc` is a symlink **into this repo**, so any installer that "adds a line to your `.zshrc`" edits the tracked dotfile and it propagates to every machine. After running one, check `git -C ~/.dotfiles diff -- zsh/.zshrc`.
- `scripts/validate-no-machine-paths.sh` enforces this. It runs in CI and in `dotfiles-backup`, which refuses to commit while it fails.

### Secrets Management
- True secrets (API keys, tokens) must never be committed and are ignored by Git.
- Secrets should be manually placed in `~/.config/dotfiles/secrets.env` (mode 600), as plain `KEY=value` lines with no `export` prefix and no `$` or backslashes in values. `.zshrc` sources it with `set -a` (refusing it unless group/other have no access) and `bin/claude-env-load` loads it as data for the foothold and `claude-remote` sessions, so it is the single place for env-var secrets. `dfctl apply` creates it empty with mode 0600 and tightens a looser mode it owns; it also restricts `~/.config/dotfiles` to 0700 (with a warning), since a group-writable directory would let others replace the file, and the step fails (offering rollback) when it leaves the file unprotected.
- `~/.zshrc.secret` remains an optional, shell-only file (aliases, functions) sourced by `.zshrc`; the foothold unit never reads it.

### Git Configuration
- The repository uses a layered Git configuration.
- `~/.dotfiles/git/.gitconfig` is stowed to `~/.gitconfig` and carries the shared non-identity settings (`core`, `gpg`, `commit`, `tag`, credential helpers) directly.
- The `git tidy` alias in `git/.gitconfig` runs the zsh function `git-tidy` (`zsh/.config/zsh/functions/git-tidy`) in a bare `zsh -f`, so the function must not depend on anything from `~/.zshrc`. It deletes local branches whose work is in the base branch (an ancestor, or a merge that changes nothing, which is how a squash or rebase merge looks) and removes their worktrees. It asks before changing anything and never touches unmerged work: a dirty or locked worktree, an unmerged branch and a branch with a gone upstream whose work is not in the base are listed and kept. Keep it that way, and keep `tests/test_git_tidy.py` in step.
- `git/.gitconfig` carries no identity of its own — it includes `~/.gitconfig.local` (written by `dfctl apply` on first run) for name/email, and conditionally includes `~/.dotfiles-overlay/git/gitconfig-work` (an optional sibling repo, not part of this one; the legacy `~/.dotfiles-private/git/gitconfig-work` is listed too) for a work-specific override.

## Maintenance & Workflows

### Development Checkout
- `~/.dotfiles` and `~/.dotfiles-overlay` are for `dfctl` only. They stay on `main` apart from a `propose` backup branch, which they keep until its PR merges (`git switch main && git pull`): stow symlinks point into them, so switching branches there changes live config. Never develop in them.
- Develop in the clones `~/Workspace/austek/dotfiles`, `~/Workspace/austek/dotfiles-overlay` and `~/Workspace/austek/ustekai-skills`. Branch from `origin/main` there, or for parallel work add a worktree of the clone (`git worktree add ~/Workspace/austek/<repo>-wt/<slug> -b <branch> origin/main`). Never run `dfctl apply` or `stow` from a worktree: `apply` refuses to run when the dotfiles checkout or the overlay is a linked worktree (exit 1, detected by a `.git` file in the checkout) unless it is a `--dry-run`, because stow would link `/etc` and `$HOME` into the worktree and break them once it is removed.

### Modifying Configurations
- Edit configuration files directly inside their respective `stow` packages (e.g., `zsh/.zshrc`, relative to your worktree).
- Symlinks are managed by `stow <package-name>` (to create) and `stow -D <package-name>` (to delete).
- `dfctl apply --force` moves files that block stow to `~/.local/state/dotfiles/stow-backups/<timestamp>/<path relative to $HOME>` and logs each move, then stows. Without it, a conflict fails the install with a hint to re-run with `--force`. Never make force the default.
- Manual stowing is for quick adjustments; `dfctl apply` handles it automatically (`stow.py`).
- `apply` splits into a user stage and a system stage. The system stage is the steps in `install_flow.SYSTEM_STEPS` (apt install, upgrade and removal, snapd, apt sources, GitHub `.deb`s, the sudo release installs of `install_system_tools` (zoom and Antigravity; `system_check` counts a missing zoom and an absent or outdated Antigravity build; the pinned release binaries, istioctl and awscli are not here, they install into `~/.local/bin` in the user stage and never trigger the sudo prompt), docker group, login shell, default terminal); only it needs sudo. By default `system_check.system_stage_reasons` decides, read-only, whether it has anything left to do and the sudo prompt is skipped when it does not. `--system` forces the stage, `--no-system` skips it. A new sudo step must be added to `SYSTEM_STEPS`, and to `system_check` if its state can be checked without root.
- `dfctl apply` exits 2 when no preset is saved and none is passed, 3 on settings drift, 4 when every step succeeded but saving the state, the opt-out migration or the move of another preset's package file failed (a failed migration write keeps the prior applied-package list, which is empty when this preset has no prior state), 130 on Ctrl-C and 1 on any other failure.
- Steps that change the system record what they did in `~/.dotfiles-setup-rollback.log` (`RollbackLog.track`); a failed install offers to undo them via `rollback.py`. A new step that touches system state must record its undo entry there.

### Development Tasks
- `mise.toml` pins the dev tools (`python`, `uv`, `shellcheck`) and defines the tasks CI runs: `mise run lint-shell`, `lint-python`, `test`, `smoke`, `completions`, `check-python`, `ci`, and `e2e <preset>` for the container install. CI calls these tasks, so a local `mise run ci` reproduces it.
- `mise` is in the default `apt_common.txt` package list and installs from its own apt repository (with `apt/etc/apt/sources.list.d/mise.sources`), but `dfctl` must keep working on a bare machine without it, and the machine's own tools are still installed by `dfctl`, not `mise`.
- Renovate bumps the `mise.toml` pins; `uv` is grouped with the installer URL in `vendor_installers.py`, whose digest in `packages/checksums.txt` Renovate cannot recompute. After such a bump run `mise run pin` (optionally with a URL substring to limit it), which re-records the stale digests from the live downloads, and review the diff: it trusts whatever the URLs serve now. `pin` only updates the digest of a URL that is already listed: Renovate rewrites the listed URL in its own bump PR, but after a hand bump change the URL in `checksums.txt` first, or the installer refuses it with "no digest recorded". A line that does not parse as `<sha256>  <url>` is reported as an error. `mise run pin-check` only reports and exits non-zero on drift; the scheduled `pin-check` workflow runs it nightly, outside the PR checks, so a moving installer URL (rtk, oh-my-zsh, rustup, SDKMAN, CodeRabbit) shows up as a red nightly before it breaks an install. The logic is `dotfiles_setup/pin_checksums.py`.

### Saving Changes
- Use `dfctl propose` to save drift in the live checkouts (`~/.dotfiles`, `~/.dotfiles-overlay`): hand edits and lines installers add. Planned changes go through branches and PRs from the `~/Workspace/austek/` clones, never through `propose`. Three deprecated commands still work and print a notice; remove them one release after this lands: `dotfiles-backup [save]` runs `propose`, `dfctl install` runs `apply`, and `dotfiles-setup` forwards its arguments to `dfctl`.
- Run `~/.dotfiles/bin/dfctl propose` only: it acts on the checkout that holds the running executable, not the working directory, and refuses to run in a linked worktree (exit 1), for the public repo and for the overlay. That executable does not look at the Workspace clones unless `DOTFILES_OVERLAY_ROOT` points to one. Keep that variable unset, or set it to the live overlay checkout, for this workflow.
- This helper script stages changes, validates the staged files with `scripts/validate-no-machine-paths.sh --staged` (on failure it runs `git reset -q` and aborts before any branch or commit), lists the new untracked files it adds, commits with `chore: update configs and package lists NO_ISSUE`, pushes the current branch (creating `backup/<timestamp>` when on `main`), and opens a PR if none exists. `main` is protected (PR + CI required); never push to it directly.
- When the overlay (`~/.dotfiles-overlay` or `$DOTFILES_OVERLAY_ROOT`) is its own git repo, `propose` then repeats the same branch/commit/push/PR flow there. The path checks (tracked and staged) and the `claude/.claude/settings.json` preflight run on the public repo only, and a failure in one repo does not stop the other.
